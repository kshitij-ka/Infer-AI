# Security

This document explains every security hardening measure in this application, why it exists, and what it does not cover.

## Response headers

Every response carries these headers, set by `app/core/middleware.py`, with one narrow exception: a CORS preflight OPTIONS request is answered directly by CORSMiddleware, the outermost layer in the middleware stack described in app/main.py, before the request ever reaches SecurityHeadersMiddleware further in, so a preflight response does not carry these headers. This does not matter in practice, since a preflight response has an empty body and no content for the missing headers to protect.

- `X-Content-Type-Options: nosniff` stops a browser from guessing a different content type than what the server declared, which prevents a JSON response from being reinterpreted as HTML or JavaScript.
- `X-Frame-Options: DENY` stops the API from being loaded inside an iframe, which is not a legitimate use case for a JSON API and closes off clickjacking against any accidentally browser rendered error page.
- `Referrer-Policy: no-referrer` stops the browser from sending this API's URLs, which can contain no sensitive query parameters today but might in the future, to other sites in the Referer header.
- `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src https://fonts.gstatic.com; img-src 'self'; connect-src 'self'; frame-ancestors 'none'` denies every content source by default, then allows exactly what the static frontend (`app/static/`, see docs/frontend.md) needs: same origin scripts, images, and `fetch()` calls; same origin stylesheets plus inline `<style>` blocks (both `index.html` and `console.html` define their page-specific layout inline rather than as a second external stylesheet; `'unsafe-inline'` is safe here since neither page ever writes user- or LLM-controlled text into a `<style>` tag or a `style=""` attribute); and the Google Fonts CDN the design system's CSS imports its typefaces from. This replaced an earlier fully-deny policy that predated the frontend and blocked every stylesheet, script, and font the console and API reference pages load, which went undetected until the pages were opened in a real browser (curl-level API testing never exercises a CSP, since CSP is enforced by the browser, not the server or curl). The first fix attempt allowed `style-src 'self'` without `'unsafe-inline'`, which fixed the external `base.css`/`tokens.css` load but still silently dropped every rule in each page's own inline `<style>` block, producing a page with the right fonts/colors but a collapsed, non-grid layout, a bug only visible by actually rendering the page in a browser, not by any of the curl-level or unit-level checks run during development.

## CORS

`CORS_ALLOWED_ORIGINS` is a comma separated list of allowed origins. An empty value, the default, allows no cross origin requests at all. The setting cannot be set to a literal `*`: a Pydantic validator in `app/core/config.py` rejects it at startup. This was not the original design. An earlier version of this document argued a wildcard origin was safe alongside a bearer token scheme, reasoning that CORS does not bypass the Authorization header requirement. A security review found that reasoning incomplete: this application hardcodes `allow_credentials=True` on the CORS middleware, and Starlette responds to a wildcard-plus-credentials configuration by reflecting the literal request Origin back to the caller rather than rejecting it, which lets any site read a credentialed cross origin response if the browser ever attaches a credential to the request (a cookie, or a cached Authorization header from client side script). The validator closes this off by refusing to start with `*` in the origin list at all, rather than relying on operators to avoid it. 

## Request body size limit

`MAX_REQUEST_BODY_BYTES` (default 65536, minimum 1024, enforced by a validator in `app/core/config.py`) bounds the size of any request body. The enforcement happens in `app/core/body_limit.py`, which counts bytes as they arrive from the ASGI receive stream and rejects the request with 413 once the running total crosses the limit. An earlier version of this middleware only checked the Content-Length header, which a request using chunked transfer encoding (no Content-Length header at all) bypassed entirely, letting an attacker stream an unbounded body past the check. A security review caught this before it reached production. The current implementation counts real bytes regardless of what the client claims in headers, so the limit holds against a chunked request the same way it holds against one with an honest Content-Length.

## Generic error responses

Any exception not handled by a specific route gets caught by a global handler in `app/main.py` that logs the full exception server side and returns a fixed body, `{"detail": "Internal server error"}`, with no exception message, type, or traceback. This stops an attacker from learning internal file paths, library versions, or query structure from an error response.

## JWT secret strength

`JWT_SECRET_KEY` must be at least 32 characters, enforced by a Pydantic validator in `app/core/config.py`. The application refuses to start with a shorter secret rather than accepting one and being vulnerable to offline brute force against a captured token signature. 

## Non root container user

The Docker image runs the application process as `appuser`, created in the Dockerfile, rather than root. A container escape or arbitrary code execution vulnerability in a dependency then does not hand an attacker root inside the container.

## Login rate limiting

`/auth/login` is rate limited per username and client IP combined (`LOGIN_RATE_LIMIT_PER_MINUTE`, default 10 per minute), independent of the chat endpoint's rate limit. The key is built by hashing the username and the client IP separately with SHA-256 and combining the two digests, rather than concatenating the raw values with a delimiter. The first version of this key concatenated username and IP directly, separated by a colon, which meant a crafted username containing a colon could alias into another user's key (a username of `victim:1.2.3.4` from any IP produced the same key string as username `victim` logging in from IP `1.2.3.4`), letting an attacker exhaust a specific victim's login attempts as a targeted denial of service. Hashing each component separately before combining them removes this: a hash digest is a fixed length hex string that cannot itself contain the separator character, so no crafted input in one component can bleed into the other.

## Login rate limit bypass via malformed request body

A cross-feature security review found that the per-username-and-IP login rate limit described above could be bypassed entirely by sending a malformed body to POST /auth/login (a missing password field, a non-string password, a missing username, or any other structure that fails the LoginRequest Pydantic model). FastAPI validates the request body against LoginRequest before the login() route function body ever executes, and the rate limit check only ran inside that function body, after validation had already succeeded. A request whose body failed validation got a 422 response without the rate limiter ever being consulted, which was verified empirically: 15 consecutive malformed requests from the same username and IP produced zero 429 responses. Since POST /auth/login is exactly the unauthenticated, brute-forceable endpoint the rate limiter exists to protect, this let an attacker send an unbounded number of malformed requests for free, defeating the feature entirely.

The fix adds a second, coarser layer: `LoginIPRateLimitMiddleware` (`app/core/login_rate_limit.py`), registered only for POST /auth/login, which runs as ASGI middleware before FastAPI attempts to parse or validate the request body at all. It checks a rate limit keyed on client IP alone (`IP_ONLY_LOGIN_RATE_LIMIT_PER_MINUTE`, default 30 per minute, using the `loginip:` key prefix, distinct from the existing `login:` prefix so the two layers never share a Redis counter) and rejects with 429 before body parsing if that IP alone is already over the threshold. This closes the bypass regardless of whether the body later turns out to be well formed. 

The new layer is deliberately coarser and set to a higher threshold than the existing per-username-and-IP check, since many different legitimate accounts can share one IP (an office network or NAT behind one address), and blocking by IP alone at the same threshold as the per-account check would rate limit unrelated users off of a shared IP. The existing per-username-and-IP check inside the route function body is unchanged and remains the more precise layer for well formed requests. Both layers reuse the same `is_rate_limited` helper and the same Redis client the rest of the application uses; this is not a second, separate rate limiting mechanism.

## Rate limit key namespace collision between chat and login-IP limits

A follow up security re-review, done after the fix above shipped, found a second Critical issue that fix introduced. The chat route's rate limit key (`app/api/routes/chat.py`) was, before this fix, built as the raw, unhashed, unprefixed username: `is_rate_limited(..., key=user.username, ...)`. `LoginIPRateLimitMiddleware`'s key was `f"loginip:{client_ip}"`. Both keys pass through the same `is_rate_limited` helper, which wraps whatever key it is given as `f"ratelimit:{key}:{window}"`. Usernames in this application are unconstrained strings (3 to 64 characters, no character restrictions, per `CreateUserRequest`), so a username crafted to literally equal `loginip:<some IP>` produced the exact same Redis key as the login-IP bucket for that IP, within the same one minute window.

This was reproduced end to end: a user was created with username `loginip:127.0.0.1` through the real admin API, made enough authenticated `/chat` calls to fill the shared counter, and a completely different, legitimate user's first ever login attempt from IP `127.0.0.1` immediately got 429, purely because of the crafted user's unrelated chat activity. Anyone able to get a user created with a crafted username (through the admin endpoint, social engineering an admin, or any future self registration feature) could use this to lock out login entirely for a chosen IP address just by making ordinary authenticated chat calls, defeating the namespace isolation the login rate limiter and the login-IP middleware were both supposed to guarantee.

The root cause was not this one collision alone: every call site that built a rate limit key was inventing its own raw key string, with only the login route's key (`_build_login_rate_limit_key` in `app/api/routes/auth.py`) actually hashing its inputs. The fix centralizes key construction in one place, `build_rate_limit_key(namespace, *components)` in `app/services/cache.py`, which hashes each component with SHA-256 independently before joining them under the given namespace prefix. Every current rate limit key in the codebase now goes through this one function: the chat route's key is `build_rate_limit_key("chat", user.username)`, the login route's key is `build_rate_limit_key("login", username, client_ip)`, and the login-IP middleware's key is `build_rate_limit_key("loginip", client_ip)`. Since every component is hashed to a fixed length digest before any prefix or separator is applied, no crafted username, IP, or future component can ever alias onto a key built under a different namespace, closing off this collision and the entire class of bug it belongs to, not just the one specific case that was found.

## Pre-merge review: insecure Docker Compose defaults

A pre-merge security review of the full branch, done before merging this API into production, found that `docker-compose.yml` provisioned the `postgres` and `redis` containers with no authentication of any kind on Redis, and hard-coded default credentials (`POSTGRES_USER=postgres` / `POSTGRES_PASSWORD=postgres`) on Postgres, while also publishing both containers' ports directly to the host (`5432:5432`, `6379:6379`). Only the `api` service needs to be reachable from outside the Compose network; anything with network access to those two host ports got unauthenticated access to the full user table, including bcrypt password hashes, and to the Redis instance backing both rate limiting and the shared chat-answer cache, letting an attacker flush rate limit counters or poison cached answers served to every user.

The fix removes the host port bindings for `postgres` and `redis` (only `api`'s `8000:8000` mapping remains), requires `POSTGRES_USER`/`POSTGRES_PASSWORD` via Compose's `${VAR:?message}` interpolation, which fails Compose startup with an explicit error instead of silently falling back to a default if the variable is unset, and adds `--requirepass` to the Redis command along with a matching `-a` flag on its healthcheck, keyed off a new required `REDIS_PASSWORD` variable. `.env.example` documents all three new variables and shows `REDIS_URL`/`DATABASE_URL` with the matching credential embedded, since the application's own Redis and Postgres clients still authenticate purely through those connection strings, not through any separate mechanism.

## Pre-merge review: unbounded login credential length

The same pre-merge review found that `LoginRequest` (`app/schemas/auth.py`) had no `max_length` on `username` or `password`, unlike `CreateUserRequest`, which bounds both. A password near the request body size cap reaches `verify_password` (`app/api/routes/auth.py`), and bcrypt (via passlib) raises `PasswordSizeError` for any input over its 72-byte ceiling. That exception was not caught at the route level, so it fell through to `handle_unexpected_exception` in `app/main.py`, which does return a sanitized, header-complete 500 response rather than leaking anything, so this was never an information disclosure or a rate-limit bypass: both the per-username-and-IP and IP-only login rate limit checks still ran before this point. The impact was availability and hygiene only, turning what should be a clean `401 Invalid username or password` into a `500 Internal server error` plus log noise for any oversized login payload.

The fix adds `Field(max_length=128)` to `LoginRequest.password` and `Field(max_length=64)` to `LoginRequest.username`, matching `CreateUserRequest`'s bounds, so oversized input is rejected by Pydantic validation (422) before it ever reaches `verify_password`. No `min_length` was added to either field: a login attempt with a too-short but otherwise well formed password should still resolve to the ordinary 401 wrong-password path, not a distinct validation error that would tell an attacker anything about why their guess failed.

## What this does not cover

- The rate limiter (both `/auth/login` and `/chat`) uses a fixed calendar-minute window, not a sliding window. This is a deliberate trade-off documented in `docs/architecture.md`: a fixed window is simpler and needs fewer Redis operations per request, at the cost of allowing up to roughly twice the configured limit across a window boundary (a burst at the last moment of one minute plus a burst at the first moment of the next). For the conservative defaults in this application (10 per minute on login, 60 per minute on chat) this is a bounded and modest degradation, not a bypass of rate limiting altogether.
- `request.client.host` is used directly as the client IP for rate limiting, with no trusted-proxy handling. This is correct as long as nothing sits between the client and this application's container (true today, since `docker-compose.yml` exposes the API directly). If a reverse proxy or load balancer is added later, as `docs/architecture.md`'s production migration path describes, whoever adds it must also add explicit trusted-proxy IP checking before honoring any `X-Forwarded-For` or `X-Real-IP` header. Trusting such a header naively, once a proxy exists, would let an attacker set an arbitrary value per request and defeat the per-IP part of the rate limit entirely.
- The login rate limit key and the username database lookup are both case sensitive today, and stay in agreement because neither one normalizes case anywhere. If a future change makes the username lookup case insensitive (for user friendliness, for example) without updating the rate limit key to match, an attacker could rotate through case variants of the same username to multiply their effective attempt budget. Any change to username matching should normalize case in one shared place used by both the lookup and the rate limit key, not just one of them.
- If `request.client` is ever `None` (some ASGI transports do not set it), the client IP falls back to the literal string `"unknown"`, which collapses every such request onto one shared bucket for the IP half of the rate limit key. This has not been observed to happen under normal HTTP traffic in this application's deployment.
- No refresh token rotation or token revocation list. A compromised JWT remains valid until it expires (60 minutes by default). A production deployment handling higher value data would add a revocation list in Redis, checked on every request.
- No separate audit log of authentication events beyond what the structured logging feature (see docs/observability.md) captures in the general request log.
- No per route Content-Security-Policy tuning: the same policy applies to every route, including the static frontend and the JSON API routes, even though only the frontend routes need the allowed sources (`script-src`, `style-src`, etc.) the policy grants.
- No automated dependency vulnerability scanning in CI, since no CI system exists in this repository yet.
